# 第三讲：精读 HAL 核心实现 - 参数如何变成寄存器写入

> 目标：从“理解架构”升级到“读懂代码行为”。本讲聚焦 HAL 的真实工作流：组包、写寄存器、启动硬件、等待完成、错误回收。

## 3.1 先建立心智模型

HAL 的本质工作可以归纳为一句话：

- 把上层算子参数翻译成硬件寄存器字段，并按硬件时序安全下发。

对应到执行循环通常是：

1. 解析算子描述符
2. 写各模块寄存器（DMA/PEA/VCU/同步）
3. 启动 NPU
4. 等 done（轮询或中断）
5. 错误检查和状态清理

## 3.2 从入口函数读起：生命周期

HAL 代码阅读建议按生命周期走，不要一上来就钻单个函数。

### 阶段 A：初始化

- 复位硬件
- 配置基础寄存器
- 初始化 LUT、缓冲区、中断

### 阶段 B：单次推理

- 准备输入与地址
- 下发算子序列
- 触发执行
- 采集输出

### 阶段 C：退出与回收

- 清中断状态
- 释放上下文
- 保留 debug 信息（可选）

## 3.3 寄存器写入模式：HAL 最核心套路

在多数实现里你会反复看到这类模式：

1. 构造临时位域结构体（shadow copy）
2. 按字段填值（含位宽裁剪/低高位拆分）
3. 一次性写入 MMIO
4. 指针移动到下一个寄存器槽位

这么做的价值：

- 保证寄存器原子配置，避免中间态误触发
- 减少 MMIO 次数，降低总线开销
- 方便审计每条指令到底写了哪些位

## 3.4 典型函数群：你该重点盯什么

### 1) `dsp_reset` / `npu_init`

看点：

- 复位时序是否有“置位-清位”脉冲
- 是否先清控制寄存器再配置关键字段

### 2) `dma_iteration_x`

看点：

- 地址是否拆分为 high/low
- hop/stride 参数如何编码
- 是否处理非对齐传输标志

### 3) `gemm_execute` / `convolution_execute`

看点：

- 分块参数如何映射到寄存器
- 累加模式（覆盖/累加）切换点
- scale 地址与数据类型字段绑定关系

### 4) `vcu_execute` / `vcu_config`

看点：

- opcode 数量和地址下发逻辑
- LUT 基地址是否一次性全配置
- 数据类型转换链是否一致

### 5) `sync_config` + `npu_start` + `wait_for_done`

看点：

- 阶段依赖是否完整
- start 与 done 使能是否有顺序保护
- done 清除是否在正确时机

## 3.5 关键细节 1：地址与位宽拆分

HAL 常见处理：

- 物理地址写寄存器时只存高位
- 大字段分散到多个寄存器位段

读代码时看到 `_high/_low` 字段不要跳过，这通常是 bug 高发区。

常见风险：

1. 位移方向错
2. 掩码长度错
3. 字段跨寄存器拼接错

## 3.6 关键细节 2：启动与完成时序

复杂 NPU 的控制通常不是“一次写完”：

- 先下发参数
- 再写 start 命令
- 再切换 done 使能/状态位

如果顺序错，可能出现：

1. 假完成（旧状态未清）
2. 卡死等待（done 未正确使能）
3. 误触发下一阶段

## 3.7 `wait_for_done`：轮询 vs 中断

两种模式各有场景：

- 轮询：实现简单，适合短任务
- 中断/WFI：功耗更低，适合长任务

HAL 层要保证无论哪种模式，结束后都要统一做：

1. 清完成标志
2. 记录状态码
3. 返回可判定错误的结果

## 3.8 读 HAL 的一套实战方法

建议你用以下顺序精读：

1. 先画调用链：谁调用谁
2. 再画寄存器写入表：函数 -> 寄存器 -> 字段
3. 最后看异常路径：timeout、invalid param、unsupported op

可以用这个模板做笔记：

```text
函数名:
输入参数:
写了哪些寄存器:
触发了哪些硬件模块:
可能失败点:
返回值语义:
```

## 3.9 常见问题与定位思路

### 问题 1：`wait_for_done` 卡死

优先排查：

1. start 是否正确写入
2. 同步依赖是否导致互等
3. DMA 是否已完成搬运

### 问题 2：结果全 0 或明显错误

优先排查：

1. 地址高低位拼接
2. data type 与 scale 是否匹配
3. psum 累加模式是否正确

### 问题 3：偶发错误、难复现

优先排查：

1. 寄存器写入是否有并发竞争
2. 中断清除与下一次启动是否重叠
3. 是否缺 memory barrier 或 volatile 语义

## 3.10 本讲作业（30 分钟）

1. 在你的 HAL 代码中选一个 `dma_iteration_*` 函数，统计它写了几个寄存器。
2. 选一个 `convolution_execute` 或 `gemm_execute`，记录“输入参数 -> 寄存器字段”映射表。
3. 画出一次完整执行调用链：`sync_config -> npu_start -> wait_for_done`，并写出每步的失败点。

## 3.11 作业参考答案（公布答案）

### 题 1 参考答案

`dma_iteration_*` 一般不是“只写 1 个寄存器”，而是按迭代层级写入多条配置指令。

- `iteration_2`：通常对应 2~3 组核心字段寄存器
- `iteration_3`：通常更多一组 stride/hop 组合
- `iteration_4`：通常为最多的分层搬运字段

结论：寄存器数量随“循环层数和地址编码复杂度”增长，而不是随函数名线性等价。

### 题 2 参考答案

以卷积为例，典型映射关系是：

- 维度参数（宽高/通道分组）-> PEA 配置字段
- 地址参数（ifmap/weight/psum/scale）-> 地址寄存器高低位
- 模式参数（类型、累加、padding）-> 控制位字段

核心检查点：

1. 地址字段是否对齐并拆分正确
2. 数据类型与 scale 地址是否同一量化策略
3. 累加模式与分块顺序是否一致

### 题 3 参考答案

一次完整调用链可写成：

1. `sync_config`：配置阶段依赖与各引擎指令入口
2. `npu_start`：触发执行并设置完成信号策略
3. `wait_for_done`：等待并回收状态

每步主要失败点：

- `sync_config`：依赖配置错误导致死锁或阶段错序
- `npu_start`：启动位未生效、done 使能顺序错误
- `wait_for_done`：中断未到达或状态位未清导致卡死

## 3.12 本讲小结

第三讲最重要的收获是：

1. HAL 不是“业务逻辑层”，而是“硬件协议层”。
2. 读 HAL 的关键在寄存器字段与时序，不在函数名本身。
3. 调试 HAL 的关键路径是“地址编码 + 同步依赖 + 启停状态机”。
